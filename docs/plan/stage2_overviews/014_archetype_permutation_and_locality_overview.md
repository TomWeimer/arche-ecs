# Module 014: In-Place Archetype Permutation & Cache Locality — Overview

## 1. Architectural Mission
In flocking and swarm simulations with 100,000 to 1,000,000+ entities, the primary frame bottleneck is **spatial neighbor search** (Reynolds separation, alignment, cohesion, and spatial hashing).

### The Cache Thrashing Problem
Even with an optimal spatial grid, as entities move dynamically through 2D or 3D space, boids that are physical neighbors end up scattered across 30 to 600 different 64 KB memory chunks. Fetching their positions during distance calculations causes continuous CPU L1/L2 cache misses.

### The Architectural Boundary
- **`colony` (Consumer):** Understands 2D/3D world bounding boxes, cell coordinates, bit-interleaving Morton codes (Z-order 2D/3D curves), and radix sorting keys.
- **`arche-ecs` (Library):** Understands raw memory, 64 KB chunk columns, and the `SlotMap` routing table. Zero spatial or dimension-specific logic!

The mission of Module 014 is to provide a **domain-agnostic, generic in-place archetype permutation engine**:
- Permutes contiguous SoA component columns across chunks based on an external permutation vector.
- Synchronizes the generational 64-bit `SlotMap` routing table in $O(N)$ time so that **all existing `Entity` handles remain 100% valid**.
- Enables `colony` to cluster spatial neighbors into the **exact same CPU cache line**, delivering a $2\times \text{ to } 4\times$ speedup on 2D and 3D neighbor searches.

---

## 2. Key Capabilities & Interfaces

### 2.1 Generic Archetype Permutation Primitive
```cpp
// Applies a consumer-provided permutation map to an archetype's chunk columns
void apply_permutation(Archetype* arch, std::span<const uint32_t> old_to_new_indices);
```
- Accepts an array mapping `old_entity_row -> new_entity_row` (generated by Colony's Radix Sort).
- Executes an in-place cycle-chasing permutation across all component columns simultaneously.

### 2.2 In-Place Comparator Sorting (Optional Convenience)
```cpp
template <typename Component, typename Compare>
void sort_archetype(Archetype* arch, Compare&& comp);
```
- Sorts rows based on an in-place component comparator (e.g., sorting particles by lifespan or depth).

### 2.3 SlotMap Routing Table Synchronization
- As entities are permuted across rows and chunk boundaries, their `SlotMap` `EntityRecord` (`chunk` pointer and `row` index) are updated in-place:
  ```cpp
  // O(1) per entity during O(N) sweep:
  slot_map.update_record(entity, new_chunk, new_row);
  ```
- **Zero Dangling Handles:** Any system holding an `Entity` handle immediately continues reading valid memory at the entity's new cache-clustered location.

---

## 3. Subsystem Modifications
- **`Chunk` (`chunk.hpp`):** Implement in-place column row swapping and inter-chunk row relocation.
- **`SlotMap` (`slot_map.hpp`):** Provide a bulk record update interface `update_record(Entity e, Chunk* new_chunk, uint32_t new_row)`.
- **`World` (`world.hpp`):** Expose `world.apply_permutation(archetype, permutation)` and `world.sort<Component>(comparator)`.

---

## 4. Invariants & Performance Target
- **Hard Invariants:** Zero game/spatial logic in the library; all existing 64-bit `Entity` handles remain strictly valid; zero chunk memory leaks.
- **Performance Budget:** In-place permutation of 1,000,000 entities across 625 chunks in $< 15\text{ ms}$ (run amortized or periodically every $N$ frames in Colony).

---

## 5. Verification & Testing Strategy
- **`archetype_permutation_tests`:**
  - Verify sort correctness against descending/ascending integer keys.
  - Verify all component columns remain aligned with their respective entity IDs after sorting.
  - Verify that `world.get_component<T>(entity)` returns the correct data for every entity before and after permutation.
